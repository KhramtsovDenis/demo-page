## Что это

Проект Healbe Release Hub: статический HTML-инструмент без backend для:

- недельных продуктовых отчетов;
- продуктовых направлений;
- дорожных карт;
- подготовки файлов для GitHub Pages.

Пользователь не программист, поэтому ответы нужны короткие, без лишнего кода. Если решение выглядит неправильным, с пользователем можно и нужно спорить.

## Последняя важная логика

- Локальный черновик новой недели должен показываться выше опубликованных старых недель, если он новее по дате.
- Опубликованный отчет скрывает только локальный дубль той же недели.
- При создании новой недели очищаются недельные поля:
  - `artifactNote` / “Сделано”;
  - `focus` / “Риски / Фокус CEO”;
  - `ceoFocus`.
- Завершенные задачи из прошлой недели при создании новой недели должны уходить в архив завершенных проектов, а не в “Завершено на этой неделе”.
- Статус отчета показывается на главной, а не внутри самого отчета.
- Скрытые, архивные и завершенные задачи не участвуют в Jira-синхронизации.

## Правила дашборда

- Главный dashboard работает от данных задач, а не от ручных дубликатов.
- Даты релизов на главном dashboard и в раскрытом формате должны подтягиваться из задач автоматически.
- План направления лучше считать по самой дальней активной задаче внутри направления: это честнее показывает горизонт направления, а не ближайший маленький релиз.
- Релизная шкала в карточке задачи всегда состоит из 12 окон: 1 окно = 1 месяц года.
- Любая дата релиза внутри месяца подсвечивает номер этого месяца: сентябрь = 9, октябрь = 10, декабрь = 12.
- Релиз в новом году снова начинается с 1: январь 2027 = 1, а не продолжение нумерации 2026.
- Не создавать отдельный релизный номер под каждую конкретную дату.
- Если у задачи нет продуктовой группы, она должна попадать в конец списка, а не пропадать.
- При создании задачи проект выбирается явно из выпадающего списка, автоопределение по тегам не использовать как основную логику.

## Jira-ключи

Правило: ключ в отчете должен совпадать с реальным ключом в Jira.

Таблица соответствий не нужна по умолчанию. Если есть расхождение, лучше исправить ключ в отчете.

Исключение: `РУ (RU-*)`. Это группа задач, поэтому в отчете можно указывать wildcard. Для синхронизации и часов по РУ нужно брать все подходящие `RU-*`.

## Jira-статусы

Нормализация статусов для отчета:

- `test` = Jira `Проверка`;
- `paused` = Jira `ON HOLD`;
- `discovery` = Jira `Backlog`;
- `in-progress` = Jira `В работе`.

## Jira Sync Lab

Тестовая страница:

`weekly-reports/jira_sync_lab.html`

Она сравнивает текущий недельный отчет с Jira-снимком и помогает подготовить patch-файл для импорта в отчет. Боевой отчет сама страница не меняет.

Текущее поведение:

- сравнение разбито на блоки: даты релиза, статусы, готовность, контрольные точки, часы для контроля, тезисы недели;
- patch можно скачать кнопкой `Скачать patch для отчета`;
- по умолчанию в patch включены даты релиза и готовность;
- статусы, контрольные точки и тезисы недели включаются вручную;
- часы пока не применяются автоматически в patch, но должны быть следующим этапом после добавления нормального Jira-снимка с worklog по людям;
- пустые значения из Jira не должны затирать заполненные поля отчета;
- диагностические заметки в снимке хранить как `syncNotes`;
- реальные тезисы для отчета хранить как `weeklyNotes` или доставать из Jira-комментариев с понятной меткой.

## Проверка

Не использовать Edge headless как основной способ проверки.

Стандартный способ:

1. Запустить локальный сервер:

   `powershell -ExecutionPolicy Bypass -File tools\serve-local-preview.ps1 -Port 5317`

2. Открывать через встроенный браузер Codex:

   `http://127.0.0.1:5317/`

`file://` для проверки новой версии не использовать.
